# Security boundary

## Implemented controls

- Startup defaults to `SIMULATION`. `DEMO`, `LIVE`, invalid modes, and `ASTRA_LIVE_ENABLED=true` are rejected.
- The only outbound network code is the cTrader adapter's WebSocket to the hard-coded demo host `demo.ctraderapi.com:5036` over TLS (certificate verification on, default context). It is used only by the read-only `ctrader-check` command; no order path uses it while DEMO is non-executable. Plain `ws://` is refused except to loopback. Credentials come from `ASTRA_SECRET_*` environment variables through `SecretVault` and are never printed or logged.
- The dashboard binds only to loopback; browser mutations receive HTTP 405. Responses use a restrictive Content Security Policy, `nosniff`, `no-store`, and frame/referrer protections.
- The dashboard rejects requests whose `Host` does not match the configured loopback host and bound port.
- CSV imports are capped by byte, row, column, field, and issue-count limits.
- Database writes use parameterized SQL. Rendered run data is inserted with DOM `textContent`, not HTML interpolation.
- Risk checks are independent from signal generation and fail closed on uncertain account state, missing/stale data, excessive/unknown spread, missing specifications, margin, duplicate intent, size, kill switch, position cap, and daily loss.
- No secret values are included in the repository or synthetic fixture.
- Role-based permission guard (`governance`): research agents, strategies, models and LLMs cannot read secrets, change risk limits or mode, release the kill switch, clear freezes, promote models or submit order commands. Every grant and denial is an audit event. No role can grant permissions.
- `SecretVault` is the single audited secret access path (environment variables prefixed `ASTRA_SECRET_`, `HUMAN_ADMIN` only); `SecretValue` never prints its value.
- LLM output is parsed by `handle_llm_output` against a strict schema. Any deviation, or any execution field (units, size, order, stop, mode and similar), yields `NO_ACTION`. A valid response is advisory only and has no path to the gateway.
- Order submission reaches a broker adapter only through `OrderGateway`; the read-only `ctrader-check` command calls the adapter's read methods (connect, account, quote, specs, positions) directly and never submits. The adapter contract has no funds-movement operations.
- Execution boundary: every adapter's `submit_order` requires an HMAC execution permit that only the gateway issues after its checks (process-local random key, 30-second validity, single-use, bound to client id, instrument, side, size, order type, stop-loss, purpose and mode; a reused permit is refused with `permit_already_used`). Subclasses cannot override `submit_order`; the check resolves through the MRO, so a mixin cannot replace it either. A refusal ends the order `BROKER_REJECTED` with `execution_refused:<reason>`. Without a valid permit, or when the adapter's own environment guard refuses, `ExecutionRefused` is raised and nothing is sent (C-01, tests in `test_ctrader.ExecutionBoundaryTests`).
- cTrader adapter guard: refuses unless the provider reported `isLive: false`, DEMO is in `EXECUTABLE_MODES`, the adapter was explicitly built with `allow_demo_orders=True` and it is `CONNECTED`. None of these is enabled for orders in this build.
- Read-only check review (2026-10-25): `ctrader-check` builds the adapter with `allow_demo_orders=False`, never calls `submit_order` or `_send_order` (a test fails if either is reached), and counts any `ProtoOANewOrderReq`/`ProtoOAClosePositionReq` sent (must be 0). It is safe to run against a demo account.
- Structured logs (`logs.py`) replace the values of fields whose names look like secrets (`secret`, `token`, `password`, `passwd`, `api_key`, `authorization`, `credential`) with `****`, recursively. Every value of at least 8 characters revealed through `SecretValue.reveal()` is also registered and masked inside the text values of a log line (message, fields, exception text) before JSON encoding. Values never revealed through `SecretValue` are protected only by field names, so code must still not log secrets.
- `backup restore` requires `HUMAN_ADMIN` or `HUMAN_OPERATOR` (`Action.RESTORE_BACKUP`) and a reason, verifies the backup's SHA-256 and integrity before replacing anything, keeps the previous database, and freezes every account with orders until a consistent reconciliation.
- cTrader token refresh is refused unless the caller passes a `TokenStore`; none is bundled, so rotated tokens are never written to an unchosen location.
- Limitation of the permit: it stops accidental, strategy and LLM bypasses inside ASTRA. Code that deliberately imports the private permit authority could forge one; that requires a reviewed code change.

- Research attempt registry (`attempts`): every scored variant (selected, rejected, failed, interrupted) is appended to `research_attempt_events` with a hash chain (`prev_hash`, `row_hash`). Triggers refuse UPDATE, DELETE and unlinked INSERT; `astra attempts verify` detects edited, removed and reordered rows, missing triggers and a truncated tail. Promotion is refused with `attempt_log_tampered` if the chain does not verify and with `trial_count_understated` if the evidence's `variants_tested` is below the store-wide trial count.
- Research integrity (lot 4): sealed plans, holdout signatures, finished holdout evaluations, model evaluations and experiments are append-only through SQLite triggers. Promotion re-derives holdout evidence from the market bars (`holdout_bars`), binds the report to its plan, the running code and the attempt log, and allows one version per holdout. A new holdout that reuses a sealed price path is refused (heuristic detector, see RESEARCH_PROTOCOL.md).

## Repository and CI controls (Gate B)

- `main` is protected on GitHub: changes only through a pull request, required checks `quality` and `full-suite` (from the CI workflow, GitHub Actions app) on a branch up to date with `main`, rules enforced for administrators, no force push, no deletion, conversations resolved before merge. No approval count is required: the repository has a single collaborator, who cannot approve their own pull request; independent review stays a project process (separate reviewer agents), not a GitHub rule.
- GitHub secret scanning and push protection are enabled. Actions may use only GitHub-owned actions pinned to a full commit SHA; the default workflow token is read-only and cannot approve pull requests.
- The CI workflow (`.github/workflows/ci.yml`, [docs/CI.md](docs/CI.md)), not yet executed (GitHub account locked for a billing issue), has `contents: read` only (plus `pull-requests: read` for one job), uses `pull_request` and never `pull_request_target`, receives no secret, does not persist the checkout token, and has no deploy, release or merge step. `tools/ci/secret_scan.py` scans the tracked tree and the full history of each analysed commit.
- Not enabled: GitHub secret scanning for non-provider patterns (the setting did not take effect on this account), Dependabot security updates (the project has no third-party dependency; it would also open pull requests on its own).

## Web authentication (Gate Auth, branch `feat/auth-deploy`)

The dashboard (`astra.webapp`, Flask) requires a server-side session for every route except `/login`, `/api/health` (answers only `{"status": "ok"|"unavailable"}`) and `/static/styles.css`. The trading, risk and research code is unchanged and still imports no third-party package.

- **Passwords.** Argon2id via `argon2-cffi` 25.1.0, RFC 9106 low-memory profile (64 MiB, 3 iterations, parallelism 4, 16-byte salt), above the OWASP minimum; rehash on login if the profile changes. At least 12 characters, at most 256, must not contain the identifier. An unknown identifier costs the same verification as a known one.
- **No default account.** No public registration. The first administrator is created locally on the server with `astra auth init-admin` (password typed twice, or generated and shown once, never stored in clear). Generated or reset passwords must be changed at the next login and expire after 72 h.
- **Sessions.**
  - The token is 256 random bits and the browser receives only that opaque value, in the `__Host-astra_session` cookie (Secure, HttpOnly, SameSite=Strict, Path=/, no Domain). The database stores its SHA-256 digest only.
  - Sessions expire after 15 minutes of inactivity and 8 hours in any case; intermediate steps (MFA, enrolment, forced password change) expire after 5 minutes.
  - A new token is issued at login, after MFA, after enrolment and after a password change; the old one is revoked.
  - All of an account's sessions end on logout, password change or reset, MFA reset, role change and deactivation. At most 5 sessions per account.
  - Sessions survive a restart, and expired ones are deleted by `astra auth cleanup`.
  - Any session-store error answers 503, never anonymous access.
- **MFA.**
  - TOTP (RFC 6238, `pyotp` 2.10.0) is mandatory for ADMIN and OPERATOR before any data is shown; a code is accepted once (replay refused).
  - Ten single-use recovery codes (100 bits each) are shown once and stored as digests.
  - The documented recovery path for a lost device or password is local: `astra auth reset-mfa` / `reset-password` on the server, by someone with shell access. There is no public reset endpoint.
- **Throttling.**
  - Failed logins are counted per address, per (account, address) and, for unknown browsers, per account. The delay is progressive from the 5th failure (2 s, doubling) and capped at 15 minutes, and the counters decay after a quiet hour.
  - A browser that already signed in successfully holds a signed `__Host-astra_device` cookie (OWASP "device cookie"). The cookie carries an issue date checked on the server (90 days) and is bound to the current password hash, so any password change or reset invalidates it. Such a browser is throttled on its own key, so an attacker failing from other addresses cannot lock the real user out; a new browser, or one whose cookies were cleared, can still be slowed down.
  - Admin re-authentication and password changes inside a signed-in session are throttled on keys of their own (per account, and per account and address), so failed logins from elsewhere cannot block them. Residual: someone holding a stolen session can keep that account's step-up throttled; the administrator then revokes sessions and resets the password with the local CLI (`astra auth revoke-sessions`, `reset-password`), which needs no step-up.
- **Requests.**
  - Exact Host allowlist: the public name only in public mode, loopback names only in private (tunnel) mode.
  - In public mode, every request must also carry the proxy secret (`X-Astra-Proxy`, compared in constant time; 403 otherwise). The proxy reads it from a root-only include, so a local process that reaches the loopback port directly cannot pass for the proxy even if it forges Host and Origin. A second barrier, the nftables rule in `deploy/`, admits only the proxy user to that port.
  - Every state-changing request needs an allowed `Origin` and a CSRF token: HMAC-bound to the session, or to the pre-login cookie for the login form.
  - The body is limited to 64 KiB.
  - Response headers: CSP without inline code, `nosniff`, `X-Frame-Options DENY`, `Referrer-Policy no-referrer`, `Cache-Control no-store`, COOP and CORP, plus HSTS in HTTPS mode.
  - `X-Forwarded-For`/`-Proto` are read from exactly one trusted proxy hop, only when `ASTRA_TRUSTED_PROXY=1` (required in public mode).
- **Roles, checked on the server for each route.**
  - READ_ONLY: summary, runs, models, experiments, session, status.
  - OPERATOR: also orders, controls, reconciliations, audit.
  - ADMIN: also accounts and the authentication audit. Every account action requires the administrator's password again; the last active administrator cannot be disabled or demoted.
  - Web roles are not execution roles. No web route submits, cancels, releases the kill switch, clears a freeze, promotes a model or changes the mode, and `astra.auth` imports nothing from execution, brokers, risk or governance (tests enforce both).
- **Audit.** `auth_events` is append-only (triggers refuse UPDATE and DELETE) and records actor, action, target, result, time and address, never a password, token, cookie, TOTP secret or code. Anonymous Origin and CSRF refusals and repeated throttled attempts are not recorded. Failed logins still are, at a rate bounded by the throttle and the proxy limits, and the table has no retention policy yet.
- **Residual risks.**
  - TOTP secrets are stored in clear in `auth.sqlite3` (mode 0600). A copy of that file or of its backups gives the second factor of every account, so treat those backups as secrets.
  - Concurrent guesses can slip a few attempts past a throttle window (at most one per worker thread).
  - Whoever uses a generated or reset password first, within its 72 h validity, also enrols the TOTP device: deliver those passwords out of band and promptly.
  - The whole model assumes the host itself is trustworthy: on a compromised host, credentials typed into the dashboard can be captured whatever the application does.

## Known gaps

- The dashboard has authentication, sessions, roles and MFA (section above), and TLS is provided by the reverse proxy configuration in `deploy/`. These remain missing: authentication for the CLI and the execution path, a secret store, external or human-signed order authorization, and multi-user isolation of the trading data. (The internal HMAC execution permit proves only that the gateway's checks ran in this process; it is not a human signature.) The application itself listens on loopback only.
- Execution roles (`governance.Role`) are asserted by the calling code or the local CLI user, not authenticated; web roles never grant them.
- The importer limits total bytes, rows, columns, field length, and stored issue count; a size-limit error rejects the import before data is parsed.
- Reconciliation is implemented and tested against the simulated broker only. Backup and restore are tested locally with the simulator only; backups are unencrypted copies of the database and must be protected like it. No dependency scanner, SBOM, secure token store, or external service supervisor has been implemented.
- The local SQLite audit trail is not tamper-proof or externally replicated.
- The attempt hash chain is tamper-evident, not tamper-proof: whoever can write the database file can drop the triggers and rewrite the whole chain consistently (hashes included), or replace the file. Only a chain head kept outside the database (from `astra attempts list|count|verify`, stored elsewhere) and passed as `--expected-head` detects that, and only for rows up to the anchor. Attempts run without a store or against another database file are not recorded.
- Evidence anchor (lot 4): `ASTRA_EVIDENCE_ANCHOR` selects `LocalFileAnchor` (path resolved to absolute), which detects a restored older database or a rewritten attempt chain but is not tamper-proof itself; production requires an external immutable (WORM / Object Lock) adapter that does not exist yet. Without an anchor, holdout promotion fails closed (`evidence_anchor_missing`, `holdout_scored_without_anchor`). A store is bound to the identity of the anchor it was first anchored to; a fresh or different anchor is refused for a used store. A non-production anchor fails promotion (`evidence_anchor_not_production_grade`) unless the human reviewer passes `allow_non_production_anchor=True` to `promote()`, which is audited. Because the local anchor file can be rewritten by its owner, a hand-crafted anchor chain is not detected: that is what the waiver accepts. The waiver is audited but not an authenticated human approval: `Actor` roles are declared by the calling code (no user authentication), so any in-process caller can pass `Actor(..., Role.HUMAN_REVIEWER)` with the flag; the audit event only records who claimed to waive. Lot 4 round 5: a store bound to an anchor refuses unanchored holdout scoring (a file copy carries the binding row, A4-D-2), `rederive_holdout_evidence` accepts only a real `BacktestStore` and reads the consumed evaluation from its file (A4-D-1), and the binding is written before the anchor's first checkpoint so a crash in between is recoverable (A4-D-6). Structural residual A4-D-3: a new database file with a new anchor can seal and score the same plan and bars again, anchored before scoring; nothing links a new store to anchors that already recorded the holdout. Only a single production anchor per deployment that every store must use (a global registry of consumed holdout fingerprints) could close it; with `LocalFileAnchor` the remaining trace is the non-production waiver. Inherent limit: whoever holds the bars can simulate the holdout outside ASTRA (or in a copy whose binding row was deleted) without leaving any trace; the seal only governs evaluations that go through the store.
- Data provenance (lot 4 round 5): the bars' source type is sealed in the plan (`data_source.source_type`, from `--source-type` or `evaluate_strategy_walk_forward(source_type=...)`); promotion fails with `dataset_not_authentic:SYNTHETIC` (or `:SIMULATED`) and fails closed with `dataset_provenance_unknown` for a missing or `UNKNOWN` label or a plan sealed before this field. No flag at promotion overrides it. The label is still declared by whoever seals the plan: attested broker history is not implemented, so a false `HISTORICAL` label on synthetic bars is not detected.
- Evidence provenance (lot 4 round 4): the holdout attempt in the hash-chained log records the stored report's SHA-256, the trial universe and the overfitting payload; promotion re-derives PBO and DSR from the bars with that universe. `rederive_holdout_evidence` needs the store and a consumed holdout.
- Lot 4 residuals: the triggers live in the same file and can be dropped by its owner; without an anchor, restoring an older backup brings a spent holdout back (it stays non-promotable); the reuse detector is heuristic (noise, resampling factors other than two, short runs); `ModelRegistry(evidence_verifier=...)` lets in-process code replace the default verifier (and with it the re-derivation); re-derivation proves numbers follow from the bars, not that the bars are genuine.

## Reporting a security issue

Do not include credentials, account numbers, or production trading data in issue reports or test fixtures. Disable the local process and preserve the relevant log/database copy for review.
