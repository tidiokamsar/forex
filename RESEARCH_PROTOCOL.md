# Research protocol

## Current baseline

The initial strategy is a transparent simple moving-average crossover. It is included to test data-to-simulation integration, not because its performance is established. Signal logic uses closes available through the signal bar; simulated entries occur on the following bar's open. A trailing range stop uses only bars available by the signal time. Stop execution is evaluated before a strategy exit when bar data cannot establish event order.

The simulation reports the sample size and includes the configured spread, slippage, and commission assumptions in both P&L and run metadata. If a position remains open at the dataset boundary, the simulator closes it at the final close with modeled costs. P&L assumes quote currency equals account currency; spot/CFD contract, leverage, swaps, latency, rejection, and conversion behavior are not represented.

## Minimum rules for future research

1. State a falsifiable hypothesis and mechanism before running variants.
2. Fix dataset hash, time range, strategy version, parameters, costs, and metrics before evaluation.
3. Keep chronological train/validation/test boundaries and use walk-forward evaluation.
4. Fit learned transformations only on training windows and preserve a final independent holdout.
5. Compare to a no-position baseline and a simple reference; include costs, sensitivity, sample size, and uncertainty.
6. Record every variant and failure. Do not tune repeatedly against the final holdout.
7. Reject results whose advantage disappears after costs or is unstable across windows.
8. Never treat historical performance as a guarantee of future returns.

## Implemented research protocol v1

`ASTRA-WF-1.0.0` evaluates expanding chronological training prefixes, fixed validation blocks, and disjoint test blocks. The latest `holdout_bars` remain reserved after the development windows. In each fold, candidate SMA settings are scored on validation bars with `validation net P&L - validation maximum drawdown in cash`; candidates below the per-window minimum trade count are ineligible for that fold's test choice. The final holdout candidate is chosen by mean validation selection score across all validation windows, then aggregate validation net P&L, then stable candidate hash. It must meet the configured minimum trade count summed across validation windows. No test or holdout metric contributes to model selection.

Each validation and test window starts with a fresh simulated account and no carried position. Indicator warm-up uses earlier bars; only a signal from the immediately preceding bar may fill at the first window open. A position still open at a window boundary closes at that window's last close. Training, validation, test, and holdout boundaries are recorded with timestamps and row indices; test blocks do not overlap. Each evaluator truncates its input at the evaluated block end, so later bars cannot affect that result.

Reports include the exact source-byte SHA-256, a separate canonical identity SHA-256 over normalized timestamp/instrument/OHLC/volume/bid/ask bars, the source fingerprint for model contracts/research/risk/validation implementations, protocol/candidate/cost configuration, a canonical plan SHA-256, per-candidate validation outcomes, per-window test metrics, and aggregated metrics. The fixed reference is `sma_crossover@1.0.0`; the flat baseline is `NO_POSITION@1`. Costs are evaluated under the declared base assumptions and 1.5x/2x stress scenarios. Aggregated returns use a fixed initial-equity denominator per independent window; drawdown is summarized as the worst and mean window drawdown. No confidence interval or statistical significance claim is made.

The CLI command `astra walk-forward` seals the plan in local SQLite and leaves the final block `RESERVED_NOT_EVALUATED`. The first sealed plan for a canonical market-bar identity is frozen within that configured store; another plan for that same identity is rejected before test results are returned. `astra walk-forward --evaluate-holdout` recomputes the pre-holdout validation selection, records a `STARTED` attempt, then evaluates the final block once. The store's unique holdout key is the canonical market-bar identity, so alternate CSV formatting, instrument case, or timestamp offsets for identical normalized bars do not create another key. A completed retry returns the stored report; interrupted `STARTED` or failed attempts remain consumed in that SQLite store.

This remains exploratory, non-promotable evidence. The local database owner can edit or replace the file or point `ASTRA_DATABASE` to another store. Direct API use can also inspect test metrics outside this CLI seal. For a confirmatory result, freeze the procedure before accessing tests and use a fresh, independent dataset. The demo command always reads the bundled synthetic fixture and verifies its SHA-256; `ASTRA_DATA_DIR` cannot substitute a different file under the demo label.

Ordinary `astra backtest` runs require the explicit `--exploratory` flag and are classified `EXPLORATORY_FULL_HISTORY_NON_PROMOTABLE`. They score the whole CSV, which may include any nominal holdout, and must not be used to tune a sealed protocol or claim out-of-sample performance. Reports are simulation evidence only and do not authorize DEMO or LIVE execution. The SMA walk-forward evaluator has no learned transformations.

## Strategy families, features and regimes (lot 2)

- `features` (`astra-features-1.0.0`): log returns, rolling volatility, Wilder ATR and RSI, rolling z-score, Donchian channel of the *prior* bars, Kaufman efficiency ratio, SMA slope. Value `i` uses bars `0..i` only; tests mutate later bars and assert earlier values are unchanged for every feature. `TrainOnlyScaler` refuses to transform before fit and cannot be refit.
- `regimes` (`astra-regimes-1.0.0`): trend/range from efficiency ratio and slope, LOW/NORMAL/HIGH volatility from quantiles fitted on a training slice only, spread state only from real bid/ask (otherwise `UNKNOWN`), approximate UTC sessions. Each estimate carries a confidence in [0, 1] and reasons; it is a hypothesis, not a fact. Transition and scheduled-event regimes are not implemented.
- `strategies`: time-series momentum, Donchian breakout, z-score mean reversion (RANGE regime required) and the SMA baseline. Each emits a `StrategyDecision` per bar with a direction or `ABSTAIN`, an invalidation (stop), estimated cost, uncertainty and reason. Abstention is the normal output during warm-up, below thresholds, on regime mismatch or when estimated cost exceeds a move proxy. Strategies import no storage, web, broker or execution code (tested).
- `signal_backtest`: generic event-time backtester for precomputed signals, tested as equivalent to the SMA backtester on the same signals. `extended_metrics` adds expectancy, average win/loss, median, per-trade Sharpe-like and Sortino-like ratios (not annualized), max consecutive losses and a seeded bootstrap interval for the mean trade, always with the trade count.

None of these strategies has been shown to be profitable. All parameters are illustrative and untuned, and all tests use synthetic data.

## ML baseline (lot 2)

`ml.run_purged_walk_forward` compares an L2 logistic regression with a base-rate classifier on the sign of the `h`-bar forward return. Training rows whose label window reaches into the validation block (plus `embargo_bars`) are purged, and the scaler is fitted per fold on training rows only. Each fold reports accuracy, Brier score, log loss, their base-rate equivalents, `edge_vs_baseline` (base-rate Brier minus model Brier) and calibration bins. The manifest records dataset identity, feature set and spec hash, columns, parameters, code SHA-256, Python version, periods and known limitations.

`astra ml-baseline` opens an experiment (hypothesis, mechanism, plan, variants tested) before running. It closes the experiment as `NEEDS_MORE_RESEARCH` only if every fold beats the base rate (otherwise `REJECTED`) and registers the model as an inactive `CANDIDATE`. A classification edge is not trading evidence; the candidate cannot be promoted without pre-registered trading evidence after costs. On the bundled synthetic fixture the edge is large because that fixture is artificially regular; it says nothing about markets.

## Registry and promotion gates

`registry.ModelRegistry` stores experiments (rejected ones included), immutable model versions with a hashed manifest, and promotion criteria hashed at registration. Defaults: at least 30 trades, positive net P&L after costs, profit factor at least 1.1, drawdown at most 10%, positive edge versus baseline, non-negative result under cost stress, holdout required, and (lot 3) PBO at most 0.3 and deflated Sharpe probability at least 0.95 with the overfitting check required. A holdout evaluation can be recorded once per version. `promote` requires a human reviewer and refuses, with an audit event, if any criterion fails or the stored criteria or manifest hash no longer match. `rollback` restores the most recent previously promoted version after verifying its manifest hash. Shadow status observes without ordering. These thresholds are starting values, not recommendations.

### Overfitting statistics (`overfitting`, `astra-overfitting-1.1.0`)

Pure Python, deterministic, no randomness. The sources actually read, and those not accessed, are listed in `docs/references/QUANT_REFERENCES.md`.

- `probability_of_backtest_overfitting(performance, n_slices=8, metric=None, *, eligibility=None, minimum_eligibility=0)`: CSCV (Bailey, Borwein, Lopez de Prado, Zhu, SSRN 2326253, Algorithm 2.3). `performance[t][v]` is the per-period net return or P&L of variant `v` in period `t`, in chronological order. Rows are split into `n_slices` contiguous blocks `[s*T//S, (s+1)*T//S)` (all rows used, sizes differ by at most one; the paper asks for equal blocks, but within one half every variant is scored on the same rows, so the ranks are unaffected). Every combination of `n_slices / 2` blocks is in-sample once, its complement out-of-sample, each joined in chronological order. The same metric scores both halves: by default the Sharpe-like `mean / sample stdev` (`0.0` for a zero-dispersion window); `selection_score_metric(initial_equity)` reproduces ASTRA's selection rule (`net P&L - initial_equity * max drawdown % / 100` on the joined path). In-sample ties take the tied variant with the worst out-of-sample metric (then the lowest index). With `eligibility` counts, only variants whose in-sample total reaches `minimum_eligibility` can be selected; a combination without one abstains and leaves the denominator (`n_abstained`). The selected variant is ranked out-of-sample (ascending, ties take the average rank), `w = rank / (N + 1)`, `lambda = ln(w / (1 - w))`. PBO is the fraction of evaluated combinations with `lambda <= 0`, so a selection tied with the OOS median counts as overfit. `probability_oos_loss` is the fraction with a negative OOS metric (paper, section 3.2). Requirements: at least 2 variants, `n_slices` even and at least 2, at least 2 rows per slice, at most `MAX_COMBINATIONS` (20,000) combinations, a finite metric, at least one non-abstaining combination.
- `deflated_sharpe_ratio(returns, n_trials, trial_sharpe_variance=None)`: Bailey and Lopez de Prado, SSRN 2460551, eq. 1 and 2. Per-period Sharpe (`mean / sample stdev`, not annualized), population (biased) skewness, non-excess kurtosis (normal = 3, as in the PSR term `1 - skew * SR + (kurt - 1) / 4 * SR**2`; excess kurtosis would understate the standard error). The benchmark is the expected maximum Sharpe of `n_trials` null trials with variance `trial_sharpe_variance`, default `1 / (T - 1)`; the variance must be in the same per-period unit as the returns. With `n_trials = 1` it is the probabilistic Sharpe ratio against 0. `deflated_sharpe_from_moments` computes the same value from summary statistics and reproduces the paper's numerical example (SR0 0.1132, DSR 0.9004). Requirements: at least 3 finite returns, non-zero variance, a positive standard-error term. With `autocorrelation_lags=m` the serial dependence is measured (`serial_dependence`) and `T` is replaced by the effective sample size `T_eff` in `sqrt(T - 1)` and in the default null variance `1 / (T_eff - 1)`; the result records `effective_observations` and the `serial_dependence` payload.
- `serial_dependence(values, lags)`: sample autocorrelations `rho_k = sum_t (x_t - m)(x_{t-k} - m) / sum_t (x_t - m)^2`, Ljung-Box `Q = T (T + 2) sum_{k<=m} rho_k^2 / (T - k)` with its chi-square(m) upper tail (`chi_square_survival`, regularized incomplete gamma), `variance_inflation = 1 + 2 sum_{k<=m} (1 - k/T) rho_k` and `T_eff = T / max(variance_inflation, 1)`. Lo (2002, eq. 19-20) gives `Var[R(q)] = q sigma^2 + 2 sigma^2 sum_{k<q} (q - k) rho_k` and `SR(q) = eta(q) SR` with `eta(q) = q / sqrt(q + 2 sum_{k<q} (q - k) rho_k)` (`lo_scale_factor`); taking `q = T` and truncating at m lags, the Sharpe of the whole sample is `sqrt(T_eff) * SR`, so `T_eff` is the number of i.i.d. observations giving the same precision. Negative autocorrelation is never allowed to raise `T_eff` above `T` (conservative). Tested against Lo's Table 2 (AR(1), q = 12: 3.46, 2.88, 4.17).
- `resolve_trials(plan_trials, plan_trial_sharpes, sample_length, sharpe_unit, bar_seconds=None, universe=None)`: `n_trials = max(plan_trials, universe.n_trials)` (the plan's count is a floor); the variance is the largest of `1 / (sample_length - 1)`, the cross-sectional sample variance of the plan's trial Sharpes (only with at least `MIN_TRIAL_SHARPES_FOR_VARIANCE` = 5 values) and that of `universe.trial_sharpes` (same `sharpe_unit` and `bar_seconds` only, same minimum). `TrialUniverse(n_trials, trial_sharpes, sharpe_unit, bar_seconds, source)` is how a store-wide registry supplies trials run outside one plan.
- Inputs fail closed: ragged rows, non-finite or non-numeric values, booleans, strings and integers below the minimum raise `ValueError` or `TypeError`; no value is silently replaced.

### Multi-family walk-forward (`strategy_validation`, version `1.1.0`)

- Families: `sma`, `momentum`, `breakout`. Mean reversion is excluded because it needs regime thresholds fitted on each fold's training slice, which this protocol version does not implement; the exclusion is written into the plan.
- `default_candidates()` is an illustrative, untuned grid of 7 variants (3 SMA, 2 momentum, 2 breakout), not a recommendation. `candidate_id` is the SHA-256 of the canonical family, strategy name, strategy version and config. At least 2 unique candidates are required, at most `validation.MAX_CANDIDATES`, and `minimum_training_bars` must cover every candidate's and the reference's warm-up.
- Folds follow `WalkForwardProtocol`. Each block is evaluated causally: signals are computed from bars up to the block end only, then simulated with `run_signal_backtest` from the block start.
- Selection uses validation metrics only (validation selection score, eligibility by `minimum_candidate_trades`, tie-break by validation net P&L then candidate id). The final candidate has the best mean validation score across folds. Every candidate is also scored on the test blocks, after the fold's selection, only to build the PBO matrix.
- PBO matrix: one row per `PBO_PERIOD_BARS` (5) bar period of each development window (fold validation, then fold test, in order), one column per candidate. Each cell is the mark-to-market net P&L of the period: the change of realised net P&L plus the open position revalued at the bar close (`(close - entry) * direction * units`) between period closes, with half of each trade's round-trip cost charged at entry and half at exit (`mark_to_market_bar_pnl`), so a window's periods sum to its net P&L. A parallel matrix counts the trades exiting in each period. `n_slices` is the largest even number not above `min(8, rows // 2)`, so every slice has at least two rows.
- PBO selection inside CSCV: the in-sample choice and the out-of-sample rank both use `selection_score_metric(initial_equity)`, the ASTRA selection rule applied to the joined periods; only variants with at least `minimum_candidate_trades` trades exiting in the in-sample periods are eligible; in-sample ties are resolved against the selection (worst out-of-sample).
- DSR inputs: per-bar mark-to-market net return (P&L / initial equity) of the final selected candidate on the development test windows, plus its holdout bars once the holdout is evaluated (`DSR_SHARPE_UNIT`). Trial Sharpes: per-bar mark-to-market Sharpe of each candidate over its validation windows (zero-dispersion candidates omitted). `n_trials` and the variance come from `resolve_trials`, with the plan's variants as a floor and an optional `trial_universe` passed to `evaluate_strategy_walk_forward` / `evaluate_strategy_holdout_once` (not sealed in the plan, since it grows). `deflated_sharpe_probability` uses `n_trials_used`; `deflated_sharpe_probability_plan_only` uses the plan's count only and is an optimistic upper bound kept for comparison. Both use the effective sample size (policy 0.3.0) and `assess_overfitting` records `dsr_serial_dependence`.
- Return frequency of the DSR sample (policy 0.3.0). The DSR and PSR are derived for a series of returns observed at a fixed interval (Bailey and Lopez de Prado 2012, 2014: `T` is a sample length, the moments are those of periodic returns; Lo 2002 treats stationary periodic returns and their time aggregation). Per-trade returns are not such a series: trades are irregularly spaced, have different holding periods, overlap with flat time, and consecutive trades of one rule are dependent, so their count is not a sample length and their Sharpe has no fixed time unit (and is not comparable across candidates that trade at different rates). ASTRA therefore uses per-bar equity returns at the bar interval (`bar_seconds`): the mark-to-market change of equity (realised P&L plus the open position revalued at each close) divided by the initial equity, flat bars included as zeros, the same unit for every candidate and for the trial Sharpes. These returns are not i.i.d. either: a held position revalued every bar carries the price series' own dependence, and volatility clustering and on/off exposure make the distribution far from normal. The dependence in levels is measured (autocorrelations up to `dsr_autocorrelation_lags`, Ljung-Box) and absorbed through Lo's effective sample size; non-normality is handled by the skewness and kurtosis terms of the PSR. When the dependence is strong (`abs(rho_k) > max_dsr_abs_autocorrelation`) or `T_eff < min_dsr_effective_returns`, no DSR is published (`LOW_INFORMATION`). The trade-count floor (`min_dsr_trades`) is kept on top, because many bars of one held position are still one decision.
- Overfitting status: `COMPLETED` when both statistics were computed; `LOW_INFORMATION` when a minimum-information guard refused to compute one (deflated Sharpe: fewer than `MIN_DSR_RETURNS` = 30 returns, fewer than `MIN_DSR_TRADES` = 30 trades, fewer than 30 non-zero returns, a lag-k autocorrelation above `MAX_DSR_ABS_AUTOCORRELATION` = 0.3 in absolute value for k up to `DSR_AUTOCORRELATION_LAGS` = 5, or an effective sample size below `MIN_DSR_EFFECTIVE_RETURNS` = 30; PBO: fewer than `MIN_PBO_SLICES` = 4 slices, any variant with fewer than `max(2, n_slices // 2)` non-zero periods, fewer than `MIN_PBO_NONZERO_ROW_FRACTION` = 50% non-zero rows, fewer distinct rows than slices, or more than `MAX_PBO_ABSTAINED_FRACTION` = 50% of combinations without an eligible in-sample variant); `INCOMPLETE` when a computation raised (errors recorded); `UNAVAILABLE` when `astra.overfitting` cannot be imported. Missing values stay `None` and keep the registry gates unmet.
- Zero variance is tested with a relative tolerance (`1e-9` of the values' scale): float noise no longer produces enormous Sharpe ratios (it is treated as zero variance).
- Baselines: flat `NO_POSITION@1` and the SMA reference (`SmaBaselineConfig()` defaults). `edge_vs_baseline` = selected net P&L minus the larger of the flat and reference net P&L.
- Cost stress: on the holdout, signals keep base costs and simulated spread, slippage and commission are scaled by each protocol multiplier (default 1.0, 1.5, 2.0). `cost_stress_net_pnl` is the worst selected net P&L among multipliers above 1.0.
- Sealing: with a store, the plan is sealed before any window is scored. One plan per canonical dataset identity per store; the table is shared with `walk-forward`, so a different plan for the same bars in the same store is refused whichever command sealed first. The holdout is scored once: selection is recomputed from bars and must reproduce the sealed plan, a `STARTED` record is written first, a completed retry returns the stored report, and a `STARTED` or failed attempt stays consumed.
- The implementation hash covers `models`, `research`, `risk`, `features`, `regimes`, `strategies`, `signal_backtest`, `validation`, `strategy_validation` and `overfitting.py`; a change after sealing makes the holdout refuse to run.
- `holdout_evidence` returns exactly the registry `EVIDENCE_FIELDS`.

### Registry gates

New evidence fields: `pbo`, `deflated_sharpe_probability`, `variants_tested`. New criteria: `max_pbo` (0.3), `min_deflated_sharpe_probability` (0.95), `require_overfitting_check` (true). New failures: `overfitting_check_missing` (any of the three missing or non-finite, or `variants_tested < 1`), `pbo_above_threshold`, `deflated_sharpe_below_threshold`. Criteria stored before lot 3 lack these keys and load with the new defaults, so legacy candidates without overfitting evidence fail closed. The check can be disabled only at registration (`require_overfitting_check=False`).

### Evidence provenance

Holdout evidence is never trusted as numbers. `record_evaluation(kind="holdout")` requires an authorized actor and the identifier of the stored holdout evaluation. At promotion, `verify_holdout_provenance` requires that this evaluation is `COMPLETED`, belongs to the plan (`plan_sha256`) and selected the candidate (`candidate_id`) recorded in the version manifest, started **after** the version was registered (criteria frozen before the holdout was seen), and that the evidence recomputed from the stored report equals the recorded values. Failures: `evidence_provenance_missing`, `holdout_evaluation_not_found_or_incomplete`, `holdout_from_another_plan`, `holdout_selected_another_candidate`, `criteria_registered_after_holdout_was_scored`, `evidence_does_not_match_holdout_report`. The manifest is also bound to what was evaluated: its `params` must equal the report's `selected_config`, and its `code_sha256` and canonical dataset identity must equal the sealed plan's `implementation_sha256` and `dataset_identity_sha256` (`manifest_params_differ_from_evaluated_candidate`, `manifest_code_differs_from_sealed_plan`, `manifest_dataset_differs_from_sealed_plan`). One holdout evaluation can back only one version. Promotion criteria may be stricter than `PromotionCriteria()` but never looser: `register_candidate` refuses lower minimums, higher maximums, or `require_holdout`, `require_overfitting_check` or `require_cost_stress_non_negative` set to False (so validation-only promotion is impossible). The floor is code and changes only through review, and it is re-applied at promotion (`criteria_below_policy_floor:<name>`), so rows stored before it existed cannot use lax criteria. The CLI refuses `--register` once the plan's holdout has been scored.

Lot 4 additions. The stored report is bound to its sealed plan (`holdout_report_names_another_plan`, `holdout_report_dataset_differs_from_plan`, `holdout_candidate_not_in_sealed_plan`), to the code that runs now (`code_changed_since_holdout`) and to the attempt log (`holdout_attempt_missing_from_log`); one version per holdout is re-checked at promotion, the first recorded version owning it (`holdout_backs_another_version`). Above all, with the default verifier the holdout is **re-derived from market data** before promotion: `check_promotion(model_id, version, holdout_bars=...)` and `promote(..., holdout_bars=...)` rebuild the sealed plan from the bars (it must hash to the same manifest), reselect the candidate on validation windows, simulate the holdout again and compare the selected candidate, trade count, net P&L, profit factor, drawdown, edge and cost stress with the stored report (`holdout_not_rederived_from_market_data` without bars, `holdout_rederivation_failed:<error>` when the bars do not reproduce the plan, `holdout_report_differs_from_rederivation`). A report minted through the store API, or forged in the file with the triggers dropped, therefore does not promote. Re-derivation is implemented for `strategy_validation` plans only; SMA `validation` plans fail closed (`holdout_rederivation_unsupported_for_this_plan`). Limit: it proves the numbers follow from the bars, not that the bars are genuine market data; data provenance (attested broker history) is the remaining control.

Lot 4 round 4 (C-1, C-2, P-1). The overfitting statistics are re-derived too. When a holdout is scored, the hash-chained holdout attempt records, on its `STARTED` event, the holdout's log returns and, on its terminal event, the SHA-256 of the stored `report_json`, the evaluation id, the trial universe used (count, trial Sharpes, Sharpe unit, bar seconds; taken right before the `STARTED` event) and the overfitting payload (status, PBO, DSR, trial count, DSR trade count, statistical policy). At promotion the registry requires exactly one completed holdout attempt for the plan with that record (`holdout_attempt_record_missing`, `holdout_attempt_ambiguous`, `holdout_attempt_record_incomplete`, `holdout_attempt_for_another_evaluation`), the stored report's hash to match it (`holdout_report_hash_mismatch`), and the recorded universe to match the trials logged before the attempt started (`holdout_trial_universe_differs_from_attempt_log`). It then re-derives the PBO and DSR from the re-derived development matrix and holdout returns with that universe and compares them, and `variants_tested`, with the report (`holdout_overfitting_differs_from_rederivation`). Any of these failures also counts as `overfitting_check_missing`, so stored statistics that are not confirmed never pass the overfitting gate. `rederive_holdout_evidence(bars, plan, store=..., trial_universe=...)` is no longer a holdout oracle: it requires the store and a `COMPLETED` or `FAILED` holdout evaluation of the plan, and refuses (`ValueError`) for a sealed, never-scored plan.

### Attempt registry and store-wide trial count (`attempts`, version `1.0.0`)

Every scored variant is an attempt, recorded by the library functions themselves (direct Python calls included, CLI not required) whenever a `store` is passed: each candidate of each fold (`fold_trial`) and of the run as a whole (`walk_forward_run`) in `strategy_validation.evaluate_strategy_walk_forward` and `validation.evaluate_walk_forward`, and each one-time holdout scoring (`holdout`). Each attempt stores the plan (`protocol_id`), run, experiment, candidate (and model id/version when known), family, strategy version, parameters (canonical JSON and SHA-256), code (`implementation_sha256`) and package version, dataset source hash, canonical market-bar identity, holdout content fingerprint, instrument, dataset period and evaluated window, start and finish times, metrics, a per-trial Sharpe-like value (per-bar mark-to-market validation returns, `strategy_validation.DSR_SHARPE_UNIT`, the unit of the DSR trial variance; legacy SMA `validation` runs record per-trade values) and the rejection or failure reason.

Statuses are appended events, never updates: `STARTED`, then one terminal event among `COMPLETED_SELECTED`, `COMPLETED_REJECTED`, `FAILED` (exception, written by an `except ... raise` so the error still propagates), `INTERRUPTED` (KeyboardInterrupt or SystemExit) and `ABANDONED` (`AttemptLog.abandon`, with a reason). A `STARTED` attempt without a terminal event is reported as `INTERRUPTED`.

Store-wide trial count (`attempts.trial_statistics_for_protocol(database, protocol_id)` or `trial_statistics(database, instrument=, period_start=, period_end=)`): distinct `(family, params_sha256, dataset fingerprint)` over every `fold_trial` and `walk_forward_run` attempt in the store, across every plan, run and experiment, all statuses (failed, interrupted and abandoned count), on the same instrument (unknown instruments match all), over every data period of that instrument (Lot 4: exploration on earlier or later data informs the choice too; an explicit `TrialScope` may still restrict the period). Holdout scorings are not counted (they re-score a counted candidate). The fingerprint is the canonical market-bar identity, so re-running the same plan does not inflate the count, while the same grid on another overlapping dataset counts again (conservative). A new plan, or a narrower grid, can only add trials. The result also carries `trial_sharpes` (the latest run-level Sharpe of each trial that has one) and their sample variance, for the deflated Sharpe ratio.

Registry gate (part of `require_overfitting_check`, applied in `check_promotion` whatever evidence verifier is configured): `trial_count_understated` when the evidence's `variants_tested` is below the store-wide count of the version's plan (without a known plan, the whole store is the scope), `attempt_log_missing_for_plan` when the plan has fewer recorded trials than declared candidates (plan sealed without its attempts, or attempts removed), and `attempt_log_tampered` when the chain does not verify. Recording holdout evidence also snapshots the count and the chain head into the evidence provenance. `evaluate_strategy_holdout_once` builds a `TrialUniverse` from this count and the recorded trial Sharpes and passes it to the DSR; the holdout's `variants_tested` is the resulting `n_trials_used`, so honest evidence passes the gate. Lot 4 cross-checks: every sealed plan of the instrument must have its trials in the log (`attempt_log_missing_for_sealed_plan`, so a chain rewritten without an explored plan is refused), the chain head recorded with the evidence must still be in the chain, and sealing refuses a holdout whose content fingerprint the log records as already scored, even if the seal rows were deleted.

CLI (read-only, database opened with `mode=ro`): `astra attempts list [--protocol ID] [--instrument X] [--status S] [--limit N]`, `astra attempts count [--protocol ID | --instrument X --start ISO --end ISO]`, `astra attempts verify [--expected-head ROW_HASH]` (exit code 1 when the chain does not verify). Each prints the current chain head.

Limits, stated plainly: SQLite is not tamper-proof. Triggers refuse `UPDATE`, `DELETE` and an `INSERT` that does not link to the chain head, and `verify` detects an edited row (row hash), a removed row (sequence gap, or `sqlite_sequence` ahead of the last row), reordering (sequence and previous-hash links), missing triggers and inconsistent status sequences. An owner with write access to the file can still drop the triggers, rewrite or empty the whole table and its `sqlite_sequence` row, and recompute every hash: such a consistent rewrite passes `verify` unless the chain head was anchored outside the database beforehand (printed, exported, committed or sent elsewhere) and is passed as `--expected-head`. Even then, an anchor only proves the rows up to that point were not rewritten. Exploration done without a store (`store=None`), in another database file or outside ASTRA is not recorded and cannot be counted.

### Research policy (`research_policy`, `astra-research-policy-0.3.0-provisional`)

Thresholds are provisional technical floors, versioned in code, not validated financial recommendations. An agent cannot lower them through an API, a CLI flag or a database row; a change is a reviewed code change that bumps the version, is justified here and, because `research_policy.py` and `holdout_reuse.py` are part of the research implementation hash, invalidates every holdout scored before (`code_changed_since_holdout`).

| Threshold | Value | Meaning |
|---|---|---|
| `conflict_abs_correlation` | 0.98 | holdout reuse conflict: the plan is refused |
| `suspect_abs_correlation` | 0.95 | suspect: sealed, promotion refused until a new independent holdout is used |
| `min_holdout_returns` | 16 | technical floor to run the reuse diagnostic; not enough to promote |
| `min_dsr_trades` | 30 | technical floor for a preliminary deflated Sharpe; not evidence of profitability |
| `min_dsr_returns` | 30 | DSR sample length floor |
| `min_pbo_slices`, `min_pbo_trades_per_slice`, `min_pbo_nonzero_row_fraction` | 4, 1, 0.5 | PBO information floors |
| `dsr_autocorrelation_lags` | 5 | lags m of the DSR sample's autocorrelations, Ljung-Box statistic and effective size (must equal the policy) |
| `min_dsr_effective_returns` | 30 | floor on the effective DSR sample size `T_eff` (policy 0.3.0) |
| `max_dsr_abs_autocorrelation` | 0.3 | the DSR is withheld when any `abs(rho_k)`, k = 1..m, exceeds it (policy 0.3.0) |

Policy 0.3.0 (serial dependence of the DSR sample): the three values above are provisional engineering parameters chosen before looking at any candidate, not tuned to make one pass, and they need a statistical review. `statistical_policy_below_floor` treats `max_dsr_abs_autocorrelation` as stricter when lower and `dsr_autocorrelation_lags` as a value that must match exactly. The holdout reuse thresholds are unchanged since 0.2.0; there is one version string for the whole policy.

When the trial count, the PBO matrix or the observations are insufficient, the status is `LOW_INFORMATION`, no PBO or DSR value is published and promotion is blocked (`overfitting_check_missing`). The development (walk-forward) DSR uses the plan's own trials and is informative only; the promotable DSR is the holdout's, with the store-wide trial count.

Lot 4 round 4 (P-4, P-8). Every `OverfittingAssessment` records `statistical_policy`: the `StatisticalPolicy` payload (with its version) and the floors actually applied by that call (the module constants of `strategy_validation`, read at run time). Promotion fails with `statistical_policy_below_floor` when an applied floor is below `StatisticalPolicy()` or the record is missing (`research_policy.statistical_policy_below_floor`), so a floor lowered in-process is visible; the record is part of the hash-chained holdout attempt, and the re-derivation at promotion runs under the current floors. The DSR needs trade information: without `dsr_trade_count` (at least `min_dsr_trades`), with or without a trade-count matrix, it is `LOW_INFORMATION`.

### Holdout reuse detection and calibration (`holdout_reuse`)

At seal time every new holdout is compared with every sealed holdout of the store: exact fingerprint, holdout period (same instrument), the attempt log's scored holdouts, the external anchor's consumed holdouts, and `assess_reuse`. Each pair is tried as is, against the reversed old path, against two-bar aggregations of either side, and with the sign ignored. Two statistics decide (thresholds set in policy 0.2.0, lot 4 round 4, unchanged in `astra-research-policy-0.3.0-provisional`):

- Window correlation of robust-standardized log returns (median, median absolute deviation floored at the match tolerance, clipped at 3) over aligned 20-return windows at every offset. A pair of windows counts only if it is also correlated after both windows are prewhitened by the mean lag-1 autocorrelation of the two paths, so serially correlated independent data does not create matches. `CONFLICT` from 0.98, `SUSPECT` from 0.95.
- Match share: the share of aligned informative returns equal within 5% of the new holdout's return scale. Returns are compared as they are, or minus each path's median when one path of the pair drifts (half its returns at the median), so a shared constant drift is not a match. Spans are dense windows and the whole overlap of each offset (at least 3 informative returns), so sparse (mostly flat) holdouts are compared on their moves and positions. A span with a share of at least 0.8 is judged by the binomial probability of its matches at the pair's own chance match rate (measured over every alignment, which absorbs tick grids and discrete moves), multiplied by the number of spans of its kind tested (per transform and sign): `CONFLICT` at most 1e-4 (a sparse span then counts runs of consecutive moves, not points); a whole-overlap span is `SUSPECT` at most 1e-2 (a dense window is a `CONFLICT` or nothing).
- An old holdout with fewer than 3 informative returns is recorded as `old_holdout_uninformative` and does not taint unrelated plans. If it is entirely constant (the bundled fixture's -12 tick ramp) it still matches a new holdout that repeats the constant (returns and price level) over 80% of its length: the fixture holdout with one close moved by 0.00001 is a `CONFLICT`.

The verdict is recorded, append-only, in `holdout_reuse_checks` with the policy used: `CONFLICT` refuses the plan; `SUSPECT` and `UNDETERMINED` (the NEW holdout has fewer than 3 informative returns, so it cannot be compared with anything, or a plan sealed before lot 4 without stored returns) are sealed but cannot be scored and promotion fails (`holdout_reuse_suspected`, `holdout_reuse_undetermined`); no statement by an agent can clear them, only a new independent holdout. A verdict recorded under a looser policy fails (`holdout_reuse_policy_below_floor`). Policy 0.2.0 replaces 0.1.0 (round 3): `UNDETERMINED` no longer depends on the old holdout (C-5: one flat sealed holdout made every later plan unscorable), sparse holdouts are compared instead of always being `UNDETERMINED` (C-6, P-5), and the match share is chance-adjusted and drift-free (P-6, P-9). New fields: `conflict_match_chance_probability` 1e-4, `suspect_match_chance_probability` 1e-2, `min_informative_points` 3, `scale_floor_fraction` 0.01 (returns below 1% of the largest one do not set the return scale).

Calibration (`tests/test_holdout_reuse_calibration.py`, fixed seeds, counts asserted exactly; synthetic data, so these rates say nothing about real markets). Positive sets are 200 sealed holdouts of 40 returns each (gaussian unless named); negative sets are N independent pairs. `UNDETERMINED` is listed apart: it blocks scoring, so it is neither a detection nor a pass. For 0 flagged pairs out of N, the one-sided 95% upper bound on the false-positive rate is 1 - 0.05^(1/N) (0.5% for N = 600, 2.0% for 150, 4.9% for 60).

False negatives, stated plainly: copies with noise from about 0.3x the return scale upward are increasingly missed (0.3x: 10% clear, 0.5x: 86% clear) and an arbitrarily noisy copy cannot be told apart from independent data (B-2: noise at 0.5x to 0.7x evades and stays documented, not fixed); a distinct path correlated 0.90 is mostly clear. A copy of a sparse holdout is never cleared, but with 3 or 4 moves it is often only `SUSPECT` (its moves are not improbable enough by chance to refuse the seal), and with fewer than 3 moves it is `UNDETERMINED`. Not compared: an old holdout with one or two moves (a copy of it passes), a nudged copy of a near-constant trend whose old holdout has a few moves (77% clear above), resampling factors other than two, shared runs shorter than about one window (20 returns; noisy copies need about 1.25 windows), and noisy copies of sparse paths. False positives: distinct but strongly correlated data (correlated pairs, overlapping baskets) is flagged like a copy, by design; two independent paths that both repeat the same constant return are a conflict (a constant path carries only its drift); independent pairs were never a `CONFLICT` in the sets above, but sparse binary and sub-tick-trend pairs are `SUSPECT` in up to 1.3% of pairs, and independent sparse holdouts with fewer than 3 moves are `UNDETERMINED` (about 22% of the 10%-sparse pairs). Every new seal is compared with every sealed holdout, so these per-pair rates accumulate with the size of the store. Cost (pure Python, QA machine under load, one sealed plan, before the write lock): about 0.02 s for 40 x 40 returns, 0.6 s for 500 x 500, 2.1 s for 1000 x 1000 and 4.2 s for 1500 x 1500 (round 3: 8 s and 65 s for the last two); the window correlations of one new window with every old window are computed as one big-integer product (Kronecker substitution, error below 3e-4, every pair near a threshold recomputed exactly) and match-share offsets are grouped by a sort. It is still quadratic and grows with every sealed plan.

### Evidence anchoring (`anchoring`)

An `EvidenceAnchor` keeps, outside SQLite and its backups, a hash-chained series of checkpoints: previous and current attempt-chain head, sequence number, consumed holdouts (evaluation id, status, content fingerprint), sealed protocols and experiment ids. `verify_store_against_anchor` detects a restored older database (`store_behind_anchor`, `consumed_holdout_missing`, `sealed_protocol_missing`), a divergent or rewritten chain (`attempt_chain_diverged`, `attempt_log_tampered`) and missing experiments. The store checks the anchor before scoring a holdout (`require_anchor_consistency`), refuses to seal a holdout the anchor records as consumed, and appends a checkpoint after each holdout (`anchor_now`). Promotion fails without an anchor (`evidence_anchor_missing`), on any inconsistency (`evidence_anchor_inconsistent:<code>`) and when the holdout was never anchored (`holdout_not_anchored`).

Lot 4 round 4 (C-3, C-4, P-2). Anchor identity: an anchor's first checkpoint carries a random `anchor_id` repeated by every later checkpoint (format `1.1.0`). The first anchoring of a store records that id, the anchor kind, its absolute location and its production grade in the store's append-only `evidence_anchor_bindings` table. Verification then reports `anchor_identity_mismatch` (store bound to another anchor), `store_not_bound_to_anchor` (non-empty anchor, never-anchored store), `anchor_without_identity` (legacy anchor) and `anchor_empty_for_used_store` (an empty anchor for a store already bound or holding sealed plans or holdout evaluations). So restoring a pre-scoring backup and pointing the store at a fresh anchor file, or repointing `ASTRA_EVIDENCE_ANCHOR`, no longer re-opens a spent holdout. With an anchor configured, sealing a new plan first verifies the store (and binds a still unused store), and anchors the new plan. Relative `ASTRA_EVIDENCE_ANCHOR` paths are resolved to absolute ones. Consequence: a store used without an anchor (sealed plans or holdouts) can never be anchored afterwards; start a new store.

Scoring: with an anchor, the `STARTED` holdout attempt is anchored before any holdout number is computed (`anchor_holdout_start`) and again after completion; promotion requires the first anchored state of that evaluation to be `STARTED` (`holdout_not_anchored_before_scoring`). Without an anchor, scoring is still allowed (exploration, tests) but leaves no external trace: the report's `evidence_anchor` records `anchored_before_scoring: false` and such a holdout is permanently non-promotable (`holdout_scored_without_anchor`, `evidence_anchor_missing`). Scoring is not refused without an anchor: the residual is that such a holdout can be scored again after a restore of an older backup (B-8), but never promoted. Promotion with an anchor that is not production grade (the shipped `LocalFileAnchor`) fails with `evidence_anchor_not_production_grade` unless the human reviewer passes `allow_non_production_anchor=True` to `promote()` (and to `check_promotion()`, which reports the waiver state through that code); the flag, the anchor kind and its grade are recorded in the `model.promotion_refused` / `model.promotion_approved` audit events.

Sealing also compares a new holdout with the returns recorded by every logged holdout attempt whose plan is no longer sealed (`assess_reuse`; `CONFLICT` refuses, other verdicts are recorded), so wiping the seal tables does not let a nudged copy be scored again (P-10). Scoring refuses a plan sealed with stored returns whose reuse verdict row is missing (P-3), as well as any verdict other than `CLEAR`. Configuration: `ASTRA_EVIDENCE_ANCHOR` names a file for the only adapter provided, `LocalFileAnchor`, which is explicitly **not production grade** (`production_grade = False`): its owner can truncate, replace or delete it. The production target is an external immutable store (WORM / Object Lock or equivalent); no provider is implemented or configured, so production immutability is **not** established.

### CLI `evaluate-strategies`

Flags: `--csv`, `--source-type` (required with `--csv`), `--source-name`, `--interval-seconds`, `--folds` (2), `--minimum-training-bars` (60), `--validation-bars` (20), `--holdout-bars` (20), `--minimum-candidate-trades` (1), `--evaluate-holdout`, `--register` (requires `--evaluate-holdout`, `--model-id`, `--version`). Without `--csv` it uses the bundled synthetic fixture after its SHA-256 check. With `--register` it records an inactive `CANDIDATE` with default criteria frozen before the holdout is scored, then the holdout evidence, and returns the `promotion_blockers`. ### Limitations

- Synthetic data only; nothing here is evidence about real markets.
- Small samples make PBO and DSR weak. With CLI defaults on the bundled fixture the assessment is `LOW_INFORMATION` (16 x 7 PBO matrix with only 7 distinct rows; 28 non-zero of 40 DSR returns), so `pbo` and `deflated_sharpe_probability` are not reported and the gate stays unmet. Before the guards (independent QA, 2026-10-25), the same run reported PBO 0.0 and a DSR of 0.99997 from 3 near-identical trades: both numbers were meaningless.
- PBO (lot 4): the matrix is mark-to-market per 5-bar period and the CSCV selection uses the ASTRA rule. Remaining differences from the real selection: ASTRA's drawdown is measured per window on the realised-equity curve (updated at trade exits) and averaged over folds, while CSCV measures it on the mark-to-market path of the joined periods; CSCV resamples validation and test periods symmetrically, whereas ASTRA selects on validation windows only (inherent to CSCV). The 5-bar period length is a fixed choice; results can change with it.
- Holdout reuse (lot 4): a new plan must carry `holdout.content_sha256` and its holdout returns (at least 16), stored apart from the plan in `holdout_signatures`. It is refused when its holdout period overlaps a sealed holdout of the same instrument, when its fingerprint matches any sealed or logged holdout, or when `astra.holdout_reuse` finds a shared price path with any sealed holdout whatever the label, dates, scale, quote direction, time direction or a two-bar resampling. The detector is a heuristic (calibration and limits in "Holdout reuse detection and calibration"): a copy with noise from about 0.3 times the return scale upward is increasingly missed (half the scale: about 86% missed), resampling factors other than two and copies with only one or two moves are not compared, distinct but strongly correlated data is flagged, sparse holdouts with too few moves are `UNDETERMINED` (not scorable), and the cost (quadratic, computed before the write lock) grows with every sealed plan. Plans stored before lot 4 without returns are compared by period with every instrument only (a time-shifted copy of them passes). Without an evidence anchor, restoring an older backup brings a spent holdout back (the log lives in the same file); such a holdout was scored without an anchor and is never promotable, and the restored store can no longer be anchored. The lasting control is data provenance, not similarity search.
- Trade-count guards (lot 4): the DSR needs at least 30 trades in its sample (`MIN_DSR_TRADES`) and each PBO variant at least one trade per slice; one held position revalued every bar is not 60 independent observations. Variants that are indistinguishable (identical, noise-level or rescaled copies) make the PBO `LOW_INFORMATION`.
- Thresholds are starting values, not recommendations.
- The SQLite seal and holdout lock are advisory: the store owner can edit or replace the file or point `ASTRA_DATABASE` elsewhere, and direct API calls can inspect test windows outside the seal.
- PBO counts only the declared variants. DSR depends on an honest `n_trials` and on asymptotic approximations. Serial dependence (policy 0.3.0) is handled by Lo's effective sample size, which is an approximation: it truncates the autocorrelation sum at 5 lags (dependence at longer lags is ignored), uses estimated autocorrelations (their sampling noise, about `1 / sqrt(T)` each, can only lower `T_eff` because negative values are capped, so an i.i.d. sample typically loses 0 to 20% of `T`), treats dependence in levels only (volatility clustering is not modelled), and combines the effective size multiplicatively with the PSR's skewness and kurtosis terms instead of Lo's joint GMM / Newey-West variance (Lo 2002, eq. 14-15), which is not implemented. Thresholds are provisional. The holdout DSR uses the store-wide count from the attempt log; exploration outside the store (no store, another database file) is never counted. The trial scope is the literal instrument label (`EURUSD` and `EURUSD.X` are different). Stored trial Sharpes are all treated as being in the current plan's unit and bar size, which can only raise the variance (conservative). Trials are treated as independent (no correlation-implied reduction of N), which is conservative. The DSR is applied to out-of-selection (test and holdout) returns, which deflates more than the paper's in-sample use.
